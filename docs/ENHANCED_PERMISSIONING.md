# GoQuorum Enhanced (v2) Permissioning

As of this change the VittaGems chain enforces **smart-contract-based account and
node permissioning at the protocol level** — GoQuorum's "enhanced network
permissioning" (a.k.a. v2 / QIP714). An account that is not known to the
permissioning contracts **cannot submit any transaction**; a node whose enode is
not approved cannot join.

This replaces the situation where `contracts/VittaGems*Permissioning.sol` were
deployed but never consulted by the client (those files are kept for reference —
see [Legacy contracts](#legacy-contracts)).

## What was changed

| Area | Change |
|---|---|
| `config/genesis.json` | `qip714Block: 0` (activates permissioning enforcement from genesis) and `maxCodeSizeConfig: [{block:0,size:35}]` (the `PermissionsImplementation` contract is ~33 KB, over the 24 KB default) |
| `docker/docker-compose.yml` | every `geth` command gets `--permissioned` |
| `contracts/permissioning/quorum/` | the 8 standard GoQuorum permissioning contracts (Solidity `^0.5.3`), vendored from `Consensys/quorum@master:permission/v2/contract` |
| `hardhat.config.js` | second compiler `0.5.17` for the suite above |
| `config/permission-config.json` | generated by the bootstrap; tells geth which contracts to use and the initial policy |
| `config/operational-accounts.json` | fixed dev keypairs for the settlement service accounts (see below) |

## The permissioning suite

Deployed by `scripts/permissioning/bootstrap-permissioning.js` in constructor-
dependency order:

```
PermissionsUpgradable(guardian)
OrgManager(upgradable)  RoleManager(upgradable)  AccountManager(upgradable)
VoterManager(upgradable)  NodeManager(upgradable)
PermissionsImplementation(upgradable, org, role, account, voter, node)
PermissionsInterface(upgradable)
PermissionsUpgradable.init(interface, implementation)     # from guardian
```

The **guardian** is the deployer account
(`0x07848fEE8428a96e7350527Dd31dfE58c0E2B1eF`, the validator1 nodekey account).
It can later swap the implementation contract via `confirmImplChange`.

Deployed addresses are written to:

- `config/permission-config.json` — consumed by geth
- `deployments/permissioning-v2-deployment.json` — human-readable record

## Policy (`permission-config.json`)

| Field | Value | Meaning |
|---|---|---|
| `nwAdminOrg` | `VITTAGEMS` | initial org that owns all bootstrap nodes + admin accounts |
| `nwAdminRole` | `NWADMIN` | full-access role granted to every account in `accounts` |
| `orgAdminRole` | `ORGADMIN` | default admin role for future sub-orgs |
| `accounts` | `config/operational-accounts.json` **plus every node's nodekey account** | network administrators at boot |
| `subOrgBreadth` / `subOrgDepth` | `3` / `4` | sub-org nesting limits |

On the first restart after the bootstrap, **geth itself** performs the one-time
network boot: it creates `nwAdminOrg`, grants `NWADMIN` to every `accounts`
entry, and imports every enode from `static-nodes.json` into `NodeManager`.
Completion is observable via `PermissionsInterface.getNetworkBootStatus() == true`.

### Why node accounts must be in `accounts`

GoQuorum signs those bootstrap transactions with `stack.GetNodeKey()` — **every**
node submits its own copy, from its own nodekey-derived account. All six nodes
race; the guards in `PermissionsImplementation` (`networkBootStatus(false)`) make
the duplicates revert harmlessly.

But once the winning node's `updateNetworkBootStatus()` sets `networkBoot = true`,
any bootstrap transaction still in flight from an **unpermissioned** node account
is *denied* rather than reverted — which invalidates the whole block:

```
########## BAD BLOCK #########
Number: 13
Error: could not apply tx 0 [0xff0be7…]: account does not have permission for the transaction
```

and the chain halts. This is exactly what happened on the first attempt here,
when only validator1's node account was listed. `bootstrap-permissioning.js` now
derives all six node accounts from `network/*/data/nodekey` and unions them into
`accounts`. Verify with:

```bash
node scripts/permissioning/node-accounts.js
jq -r '.accounts[]' config/permission-config.json
```

## Rebuilding the chain with permissioning

`scripts/permissioning/rebuild-with-permissioning.sh` does the whole thing
(**destructive** — wipes chain data, keeps node keys):

```
bash scripts/permissioning/rebuild-with-permissioning.sh          # prompts
bash scripts/permissioning/rebuild-with-permissioning.sh --yes    # no prompt
```

Phases: stop + wipe chaindata → `geth init` new genesis → start (accounts still
open) → deploy suite + write `permission-config.json` everywhere → restart
(enforcement on) → wait for network boot → `verify-permissioning.js` → redeploy
`VittaGemsSettlement`.

It deliberately does **not** call `deploy-network.sh`, which regenerates every
node key (new validator/deployer addresses). `deploy-network.sh` has been updated
with the same genesis/compose changes for anyone doing a from-scratch build.

## Verifying enforcement

```
npx hardhat run scripts/permissioning/verify-permissioning.js --network quorum_local
```

Exits 0 only if: network boot complete **and** the deployer (a network admin) can
transact **and** a freshly-generated unknown wallet is rejected by the chain.
Last run:

```
[1] network boot status ......... true  ✓
[2] deployer isNetworkAdmin ..... true
    deployer self-tx accepted .. true  ✓
[3] stranger (never registered): 0xa52C315173F5b655371844cD978157bA0f196D14
    transactionAllowed(stranger) = false
    stranger self-tx ........... REJECTED ✓
    -> account does not have permission for the transaction
RESULT: ENHANCED PERMISSIONING ENFORCED ✓
```

Other helpers in `scripts/permissioning/`:

| Script | Purpose |
|---|---|
| `add-account.js` | permission a new account (grant) |
| `revoke-account.js` | suspend / reactivate / blacklist an account |
| `health-check.sh` | per-node bad-block count, permission denials, v1/v2 model, service-ready |
| `denials.sh` | every permission denial across all nodes, with client address |
| `boot-status.sh` | raw `getNetworkBootStatus()` + recent permission logs |
| `node-accounts.js` | the account each node's nodekey derives to |
| `gen-operational-accounts.js` | (re)generate `config/operational-accounts.json` |

A healthy network reports `badblocks=0` on every node. The only expected
`permDenied` is the one produced by `verify-permissioning.js`; it is caught at
the txpool, so it never enters a block.

## Managing accounts, orgs and roles after boot

### Granting a new account (the common case)

Any account not present at bootstrap — a backend API service, a new settlement
agent, an integration client — **cannot transact until it is permissioned**:

```bash
ACCOUNT=0xYourServiceAccount \
  npx hardhat run scripts/permissioning/add-account.js --network quorum_local
```

Optional `ROLE` (default `SETTLEMENT_SVC`) and `ACCESS` (default `2`). The script
prints `transactionAllowed` before and after, so you get proof rather than a
silent success. To withdraw access:

```bash
ACCOUNT=0x... ACTION=1 \
  npx hardhat run scripts/permissioning/revoke-account.js --network quorum_local
```

`ACTION`: `1` suspend, `2` reactivate, `3` blacklist.

`ACCESS` levels: `0` read-only, `1` transact, `2` transact + contract deploy,
`3` full. **Prefer a scoped role over network admin for service accounts** — a
service should not be able to vote on org changes or manage other accounts.

### Read-only inspection

The `quorumPermission` namespace is exposed over HTTP and WS:

```bash
curl -s -X POST http://localhost:8545 -H 'Content-Type: application/json' \
  --data '{"jsonrpc":"2.0","method":"quorumPermission_acctList","params":[],"id":1}'
```

`quorumPermission_orgList` / `acctList` / `nodeList` / `roleList`.

> The **write** methods (`quorumPermission_addAccountToOrg` etc.) require the
> sending key to live in a node's keystore. These nodes only carry nodekeys, so
> the scripts above talk to the permissioning contracts directly with the
> deployer key instead. Use the scripts, not the RPC write methods.

## Operational accounts

`config/operational-accounts.json` holds **fixed development keypairs** for
`deployer`, `treasuryAdmin`, `complianceOperator`, `settlementAgent`, `auditor`,
`partner1`, `partner2`. They exist because once permissioning is active an
account must be known to the contracts before it can transact — the old
`Wallet.createRandom()` pattern in the lifecycle test would break. All seven are
seeded as `NWADMIN` for simplicity.

> **Production**: do not ship these keys. Give the settlement operators their own
> org (e.g. `VITTAGEMS_OPS`) with scoped roles instead of network-admin, and keep
> `nwAdminOrg.accounts` to a small, HSM-backed set.

## Legacy contracts

`contracts/VittaGemsNodePermissioning.sol` and
`contracts/VittaGemsAccountPermissioning.sol` (plus
`scripts/deploy/deploy-permissioning.js`) are **retained but not the enforcing
layer**. They implement a Besu-style `transactionAllowed(...)` interface that
GoQuorum never calls. Keep them only as a reference / potential Besu-compat path;
the chain's real permissioning is the v2 suite described above.

## Deployment note (AWS)

`docker-compose.yml` publishes RPC ports as `"8545:8545"` etc., which binds all
host interfaces. Enhanced permissioning stops unknown *accounts*, but the RPC
endpoint itself is still reachable by anyone who can reach the port. Lock those
ports to the backend security group before any non-local deployment.
